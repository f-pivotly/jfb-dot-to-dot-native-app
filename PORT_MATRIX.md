# Dot to Dot — Port Matrix

Every behaviour in the legacy Supabase PWA (`jfb/jfb-dot-to-dot`) set against the Pivotly native app
(`jfb/jfb-dot-to-dot-native-app`). The two write to different backends — `daily_events` via Supabase
versus `jfb_daily_activities` via `core-data-write` — so what ports is **the rule, not the query**.

| Status | Count | Meaning |
|---|---|---|
| `MISSING` | 7 | Not in the native app at all |
| `DIFFERS` | 11 | Present but behaves differently |
| `PARITY` | 26 | Equivalent already, nothing to do |
| `AHEAD` | 10 | Native is better; nothing to port |
| `ARCH` | 3 | Architectural difference, needs a decision |
| **Total** | **57** | |

---

## Open work, easiest first

`XS` is minutes in one file · `S` is under an hour · `M` is a real change across a few files ·
`L` is blocked — on a decision, a schema change, or a capability the app does not have yet.

Rows 1–18 are the first pass. Rows 19–29 came out of later sweeps and are ordered easiest-first among
themselves. A row that gets **done moves to the parity table below** — as `PARITY` when it matches the
reference, `AHEAD` when it ends up better. Numbers are never reused, so the gaps here are rows that shipped
and earlier references still resolve. A bare `#N` means this table; a parity-table row is written `parity #N`.

**A rewind rule had to change for the shift-start pre-fill.** `confirmShiftStart` used to treat *any* start time in the future as
"this is a night shift that began yesterday" and subtract a day. That was harmless while the stepper only
ever showed the current time. Once it pre-fills yesterday's start, an operator opening the app at 05:30 with
a 06:00 start would have confirmed a shift beginning 06:00 **yesterday** — a 23-hour shift, with the gap
logic believing it. It now only rewinds when the time is more than six hours ahead, so a 22:00 start seen at
01:00 still rewinds and an early login does not. The PWA has both the same pre-fill and the same rewind
rule, so this is live on the iPads today.

**The three work-type rows share one blocker** — multi-layer gate (#8), delay-code filtering (#9) and Lift 1–8 (#10). The PWA resolves work type at render time from the selected machine (`effectiveWorkType()` reads the equipment row); the native app resolves it in `buildProjects`, which runs per project *before* any equipment is picked. Fix that once and all three become one-line conditions — attempt them separately and you pay for the same refactor three times.

**#27 rides on the same resolution but is not part of that refactor.** It needs somewhere for the scoping rule to *live*, and the platform has no place for it: work type is a domain column, pass type is a picklist, and nothing joins them. That is a modelling decision, not a render-time fix.

## Ten decisions that aren't mine to make

- **Whether deleting a session should void the server record.** Neither app does it today: both remove the
  row locally and leave the backend copy in place. The native app now says so in its toast; the PWA's says
  "Session deleted", which isn't true. If delete is meant to retract a record, that needs a write path and a
  policy for already-reported days — it is not a port gap, since there is nothing to port it from.
  **Mostly answered already, and by the daily app.** Retraction is a designed, permissioned, reversible PM
  action there: `operation: 'delete'` is a platform soft delete, every view filters `is_deleted IS NOT TRUE`,
  the confirm modal tells the PM it "stays recoverable", and `view_deleted_events` gates a "Show deleted"
  toggle. The operator app has none of that — no restore UI, no reason, no permission model — so "the
  operator retracts records" is not a gap, it is the system working as designed. What is genuinely open is
  narrower: **what should the operator app's delete button mean, given retraction belongs to the PM?**
  **The reference app already answers it, and the answer is (a)-plus-a-guard.** The PWA confirms, deletes
  locally, leaves a synced row alone — and, via the orphan guard in parity #30, drops the write entirely if it had
  not gone out yet. So delete means "never happened" while offline and "local only" once synced: one button,
  two outcomes, decided by a race the operator cannot see. Undocumented, but it is the behaviour the field
  has had for months. The legacy daily app carries the PM-side half (`event_deletions` with `reason` /
  `deleted_by` / `deleted_at`, filtered client-side), exactly as the native daily app does with `is_deleted`.
  So **both stacks already agree that retraction belongs to the PM** — the only question is how faithful to
  be. **(a) Confirm + keep local + port the guard** matches the reference exactly; cheapest, and the
  operator's log and the office's still drift once a row has synced. **(b) Wire the soft delete** so the
  operator's delete is the PM's delete — better than the reference, but blocked until the app keeps the
  created `core_record_id` (see #14/#28). **(c) Remove the button** — zero divergence, but a deliberate
  break from the reference, so it needs saying out loud rather than being shipped as a port.
- **Cold-start offline.** The native app cannot boot without the portal frame. If iPads go out of signal
  and reboot, that is a hard stop with no workaround in the frontend.
- **Lane / Step persistence.** Deriving the flag is a frontend change; persisting `lane` and `step` needs
  columns on `jfb_daily_activities`, which is a schema conversation with Dustin.
- **Whether favourites should follow the operator between tablets.** They are now stored per operator, but
  on the device. `jfb_operators.favourite_activity_ids` (text, nullable, no description, written by nothing)
  is where they would live server-side. Syncing costs an `updateDomainRecord` path — `data/index.js` only
  does `operation: 'insert'` today, though the platform accepts `update` and the sibling daily app already
  uses it, so this is a local wiring job — plus offline queueing, since a star tap must never fail on a barge, plus
  a decision on the column's format plainly documented in that empty description. Worth it only if operators
  actually change tablets often; if a tablet stays with its machine, local is indistinguishable.
- **Operator name without a roster.** The PWA lets an operator type their name and stores it, because
  `daily_events.operator_name` is text. `jfb_daily_activities` has only the `operator_id` FK, so the native
  fallback can unblock the shift but cannot attribute it. Either add `operator_name` text to the domain
  (mirrors the PWA, one column) or accept that empty-roster projects log unattributed sessions. Auto-creating
  `jfb_operators` rows from a field device would give a real FK but invites duplicate people, which is why
  neither app does it today.
- **One column closes #14 and #28 together: `local_id` on `jfb_daily_activities`.** Unique, nullable, text.
  The operator app already generates the UUID — `saveDailyActivity` mints one for the queue key and throws
  it away. Putting it in `recordData` makes a retried write idempotent (#14) and makes a field session
  distinguishable from a PM-entered one (#28), which is exactly the pair `daily_events.local_id` does in the
  legacy stack. Two asks, one migration. `status` is not part of it — that column is dead on both sides.
  What is not mine to decide: whether the backend dedupes on it (a unique index plus upsert-on-conflict) or
  merely stores it, and whether the native daily app should grow the `eventSource()` equivalent once it can.
- **Where the pass-type scoping rule lives** — row #27. The legacy shape (a `work_type` column on a
  `pass_types` table, scoped by both apps) cannot be expressed here: picklist values are
  `{label, value, enabled}` and the values endpoint takes no parameters. Three options, in rising cost.
  **(a) Leave it flat.** Both native apps already agree on the unscoped list, so nothing is inconsistent
  today — and once #10 lands, capping shows Lifts and the flat list is only reaching dredging anyway. If the
  picklist holds nothing capping-shaped, this is already a non-problem and #27 closes as `PARITY`; somebody
  needs to open the picklist and look. **(b) One picklist per discipline** — `pkl-jfb-pass-type-dredging`
  and `-capping`, chosen by `effectiveWorkType()`. Picklist-per-scope is the only "scoped picklist" the
  platform has. Costs a migration of existing `pass_type` text values if the slugs change. **(c) Promote
  pass types to a domain** — `jfb_pass_types` with a `work_type` column, mirroring the legacy table.
  Truest to the original and the only option that survives a third discipline, but it is a new domain, and
  both native apps plus `reportPdfData.js` would have to stop calling `fetchPicklistValues`.
  Worth noting that work type is barely modelled either: `jfb_work_types` exists as a lookup domain, but
  `jfb_projects.work_type` and `jfb_equipments.work_type` are free text that nothing FKs to, deliberately —
  "validating in application code rather than a DB CHECK". Option (c) is the only one that changes that.
- **What the session log is scoped to** — rows #5 and #11, and the "Total Hours" figure, are all one
  decision. **(A) Day-scoped:** the list and the total cover today, matching what the boot loader already
  does; #5 becomes a one-line in-memory filter and #11's grouping work mostly evaporates, because one date
  needs no headers. **(B) A window with date headers:** boot reads a range over the existing `date_idx`
  instead of a single key, yesterday stays visible under its own header, and #5 dissolves into #11.
  **Precisely what the reference does, since "the PWA's model" is easy to overstate:** `loadAllSessions`
  reads `getAllSessions()` — everything ever, no window at all — groups by date, sorts descending, and gives
  each header a real per-day total (`N sessions • X.XX hrs`). Growth is bounded only by the operator pressing
  Clear 48hr / Clear All. **So porting it verbatim depends on #3, which is `MISSING`** — unbounded history
  with no clear action is worse than either option here. Two defects are baked into that model and should not
  come with it: the bottom-line "Total Hours" sums *all* sessions, a lifetime figure that reads like an
  accident next to the per-day header totals, and the grouping key is `toISOString()`, so an evening session
  lands under tomorrow's header — the same UTC fault the native app already fixed with `localDateKey`
  (parity #24). Whichever option wins, the store still grows unbounded and needs pruning, and per-*shift*
  totals remain a third answer that neither app implements and that would need a shift marker on each row.
  The question for the field is what an operator does with that number at the end of a shift, and whether
  anyone looks back at yesterday on the tablet rather than in the daily app.
- **Whether duration is stored or derived** — row #26. The PWA writes `duration_ms` / `duration_hours`;
  `jfb_daily_activities` has neither column, and every view in `jfb_domain_bootstrap.py` computes hours as
  `EXTRACT(EPOCH FROM (end_date_time - start_date_time)) / 3600.0`. So the native app is almost certainly
  right to send only the timestamps — worth one confirmation from Dustin, then this closes as `AHEAD`.
- **Whether a mid-session correction should count** — row #25. The PWA reads Area, Pass and Notes at Stop,
  so an operator who taps the tile first and fixes the Area a minute later has it recorded. The native app
  snapshots at Start and drops the correction. Start-snapshot is more truthful about what was actually
  running; end-read matches how the guys actually tap. Whichever way it goes, both apps should do the same
  thing or the two datasets disagree about the same shift.

## Shared defects — neither app is right

Not port gaps, since there is nothing to port them from. Listed because this is the document where both
apps are in view at once.

- **Add Past Session pre-fills a UTC date.** Both derive the default from `toISOString()`, so after ~19:00
  Central the modal opens on tomorrow and the operator has to notice. The native fix is a one-line swap to
  the `localDateKey()` it already uses everywhere else (#24); the PWA's is part of the wider UTC problem in
  parity #24.
- **A night shift loses its resume at midnight.** `openShiftToday` tests `stored.shiftDate === localDateKey()`,
  and `shiftDate` is stamped at `beginShift` from the start day — so a 22:00 shift reopened at 02:00 fails the
  test and drops to `confirmSetup` instead of resuming. The boot loader compounds it: scoped to
  `localDateKey()`, it reloads only the rows dated after midnight, so the pre-midnight half of the *same
  shift* is gone from the log and from the gap anchor. The PWA has the identical check on `shiftStartDate`
  and the same day-keyed store. Night shifts are plainly real here — the shift-start rewind rule exists
  precisely so "a 22:00 start seen at 01:00 still rewinds". Fixing it properly means keying the session store
  and the resume check on the **shift**, not the calendar day, which is why it is not a one-line change in
  either app.
- **Neither app can correct a saved session.** Delete removes the local row and leaves the server copy
  standing, and the only way to re-enter it is Add Past Session — which writes a *second* server row. So a
  corrected session is two rows on the backend, one of them wrong, with nothing marking which. This is the
  delete decision above seen from the other side: whatever retracts a record is also what makes editing one
  possible.

## One thing that is not a port gap but will bite

`src/data/index.js:4` ships `const IS_LOCAL = true`, which drops the `/vm` prefix from the resolved API
base. That is a local-development switch committed in the on state — the same class of hazard as the PWA's
`js/config.js`, which is sitting on `http://127.0.0.1:54321` with the production Supabase credentials
commented out above it. Both need a deliberate flip before a deploy, and neither has anything that checks.
