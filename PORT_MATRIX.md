# Dot to Dot — Port Matrix

Every behaviour in the legacy Supabase PWA (`jfb/jfb-dot-to-dot`) set against the Pivotly native app
(`jfb/jfb-dot-to-dot-native-app`). The two write to different backends — `daily_events` via Supabase
versus `jfb_daily_activities` via `core-data-write` — so what ports is **the rule, not the query**.

| Status | Count | Meaning |
|---|---|---|
| `MISSING` | 2 | Not in the native app at all |
| `DIFFERS` | 4 | Present but behaves differently |
| `PARITY` | 33 | Equivalent already, nothing to do |
| `AHEAD` | 16 | Native is better; nothing to port |
| `DROPPED` | 2 | The reference has it; the native app deliberately does not |
| `ARCH` | 1 | Architectural difference, needs a decision |
| `DATA` | 1 | Code is correct; a configured value is missing |
| **Total** | **59** | |

## Open work, easiest first

`XS` is minutes in one file · `S` is under an hour · `M` is a real change across a few files ·
`L` is blocked — on a decision, a schema change, or a capability the app does not have yet.

Rows 1–18 are the first pass. Rows 19–29 came out of later sweeps and are ordered easiest-first among
themselves. A row that gets **done moves to the parity table below** — as `PARITY` when it matches the
reference, `AHEAD` when it ends up better. Numbers are never reused, so the gaps here are rows that shipped
and earlier references still resolve. A bare `#N` means this table; a parity-table row is written `parity #N`.

**A rewind rule had to change for the shift-start pre-fill.** `confirmShiftStart` used to treat *any* start time in the future as
"this is a night shift that began yesterday" and subtract a day. That was harmless while the stepper only
ever showed the current time. Once it pre-fills yesterday's start, an operator opening the app at 05:30 with
a 06:00 start would have confirmed a shift beginning 06:00 **yesterday** — a 23-hour shift, with the gap
logic believing it. It now only rewinds when the time is more than six hours ahead, so a 22:00 start seen at
01:00 still rewinds and an early login does not. The PWA has both the same pre-fill and the same rewind
rule, so this is live on the iPads today.

**The work-type cluster has shipped** — multi-layer gate, delay-code filtering and the Lift branch are parity #39, #40 and #41. They shared one blocker and were done in one pass: the PWA resolves work type at render time from the selected machine, while `buildProjects` ran per project *before* any equipment was picked. `effectiveWorkType(project, equipmentId)` is now exported and every derivation keys off it. **One piece is inert until a portal change:** the delay-code filter needs `jfb_work_types` in this app's data access to resolve a code's `work_type_id` to a name — without it the app fails open and shows every code, exactly as before.

**#27 rode on the same resolution but was never part of that refactor — it is now closed as parity #50.** It needed somewhere for the scoping rule to *live*, and the platform has no place for it: work type is a domain column, pass type is a picklist, and nothing joins them. The answer was to stop trying to scope one list and give each discipline its own, chosen in `passField()`. What the sweep did turn up is a plain data gap, now open as #30: the dredging picklist is missing `Residual`.

## Decisions that aren't mine to make

- **Whether deleting a session should void the server record.** Neither app does it today: both remove the
  row locally and leave the backend copy in place. The native app now says so in its toast; the PWA's says
  "Session deleted", which isn't true. If delete is meant to retract a record, that needs a write path and a
  policy for already-reported days — it is not a port gap, since there is nothing to port it from.
  **Mostly answered already, and by the daily app.** Retraction is a designed, permissioned, reversible PM
  action there: `operation: 'delete'` is a platform soft delete, every view filters `is_deleted IS NOT TRUE`,
  the confirm modal tells the PM it "stays recoverable", and `view_deleted_events` gates a "Show deleted"
  toggle. The operator app has none of that — no restore UI, no reason, no permission model — so "the
  operator retracts records" is not a gap, it is the system working as designed. What is genuinely open is
  narrower: **what should the operator app's delete button mean, given retraction belongs to the PM?**
  **The reference app already answers it, and the answer is (a)-plus-a-guard.** The PWA confirms, deletes
  locally, leaves a synced row alone — and, via the orphan guard in parity #30, drops the write entirely if it had
  not gone out yet. So delete means "never happened" while offline and "local only" once synced: one button,
  two outcomes, decided by a race the operator cannot see. Undocumented, but it is the behaviour the field
  has had for months. The legacy daily app carries the PM-side half (`event_deletions` with `reason` /
  `deleted_by` / `deleted_at`, filtered client-side), exactly as the native daily app does with `is_deleted`.
  So **both stacks already agree that retraction belongs to the PM** — the only question is how faithful to
  be. **(a) Confirm + keep local + port the guard** matches the reference exactly; cheapest, and the
  operator's log and the office's still drift once a row has synced. **(b) Wire the soft delete** so the
  operator's delete is the PM's delete — better than the reference, but blocked until the app keeps the
  created `core_record_id` the write returns — the `local_id` half is done (parity #42), this is the other half. **(c) Remove the button** — zero divergence, but a deliberate
  break from the reference, so it needs saying out loud rather than being shipped as a port.
- ~~**Cold-start offline.**~~ **Not a decision — it was already solved, one layer up.** Closed as parity #52.
  The claim here was that an iPad rebooting out of signal is a hard stop with no frontend workaround; that
  was drawn from this repo alone, which has no service worker. The portal has one, and it caches the native
  app shell, the resolve calls and the `/applications/<slug>` route specifically. What is genuinely open is
  much smaller: local testing, since the worker is deliberately not registered in development (see #52).
- ~~**Lane / Step persistence.**~~ **Done** (parity #46). The flag is derived from the work-type vocabulary and
  `lane` / `step` columns were added to `jfb_daily_activities`, so the fields now persist.

  uses it, so this is a local wiring job — plus offline queueing, since a star tap must never fail on a barge, plus
  a decision on the column's format plainly documented in that empty description. Worth it only if operators
  actually change tablets often; if a tablet stays with its machine, local is indistinguishable.

## Shared defects — neither app is right

Not port gaps, since there is nothing to port them from. Listed because this is the document where both
apps are in view at once.

- **Add Past Session pre-fills a UTC date** — **fixed on the native side only** (parity #37). Both derived
  the default from `toISOString()`, so after ~19:00 Central the modal opened on tomorrow, with a correct
  local time beside it, which is what made it easy to miss. The native app now uses `localDateKey()`. The
  PWA still does it, as part of the wider UTC problem in parity #24, and is untouched by choice — it is live
  in the field.
- **Calendar-day bucketing disagrees with itself on the server.** Not an app defect at all, but it is the
  same UTC-vs-local fault one layer down, and it is worth more than either app-side fix. `jfb_daily_activities`
  deliberately has no `report_date`: it stores `start_date_time` plus `timezone` so the day is derived
  server-side — `dvw-jfb-distinct-dates` says exactly that, and is the **one** view that does it,
  via `AT TIME ZONE COALESCE(da.timezone, 'UTC')`. **Twelve** other places cast bare `da.start_date_time::date`,
  which resolves using the database's timezone rather than the barge's. So a 19:00 Central session buckets to
  Monday for the report date picker and to Tuesday for GOH, NOH, Operating Hours, efficiency and delay hours —
  the session shows up on the day it happened, but its hours are counted on the next one, on every project.
  The fix is to bring those twelve in line with the one, not to add a client-written date column, which is
  the very thing that produced the defect above. **Verify the database session timezone first**: legacy rows
  with a null `timezone` only stay put if it is already UTC.
- **The daily app must learn the lift picklist — now live, not hypothetical.** parity #41 has shipped, so the
  operator app writes `lift_*` values today. The daily app resolves pass labels from `pkl-jfb-pass-type` alone in four places
  (`reportPdfData.js:308`, `EventLogTab.jsx:516` and `:376`, `NarrativeContextPanel.jsx:53`), each
  `passTypeLabels[v] ?? v`. Once the operator app starts writing `lift_3`, those fall through to the raw
  value — the report prints `lift_3` instead of "Lift 3" — and worse, `EventLogTab:376` builds the PM's
  **edit dropdown** from that list, so a PM editing a capping event cannot re-select the lift the operator
  chose and may blank it by touching the row. The fix is small if the right distinction is kept:
  **reading needs the union of both picklists, only the write-side dropdown needs the discipline-scoped
  subset.** Merge the two label maps once for display; scope only the dropdown. Get that backwards and the
  branching spreads to four sites instead of one.
- **A night shift loses its resume at midnight.** `openShiftToday` tests `stored.shiftDate === localDateKey()`,
  and `shiftDate` is stamped at `beginShift` from the start day — so a 22:00 shift reopened at 02:00 fails the
  test and drops to `confirmSetup` instead of resuming. **Half of this is now fixed on the native side, as a
  side effect of parity #49.** The boot loader used to compound it — scoped to `localDateKey()`, it reloaded
  only the rows dated after midnight, so the pre-midnight half of the *same shift* was gone from the log and
  from the gap anchor. It now reads the whole store, so those rows come back under their own date header and
  `latestSessionEnd()` sees them again; a resumed night shift no longer anchors its next gap to the wrong
  place or writes a bogus `STARTUP/SHUTDOWN` row to the office. **What is left is the resume check itself**,
  which still drops to `confirmSetup` — an annoyance now rather than a data fault. The PWA retains both halves,
  with the identical check on `shiftStartDate` and a store keyed on a *UTC* day. Night shifts are plainly real
  here — the shift-start rewind rule exists precisely so "a 22:00 start seen at 01:00 still rewinds". Closing
  it properly still means keying the resume check on the **shift** rather than the calendar day.
- **Neither app can correct a saved session.** Delete removes the local row and leaves the server copy
  standing, and the only way to re-enter it is Add Past Session — which writes a *second* server row. So a
  corrected session is two rows on the backend, one of them wrong, with nothing marking which. This is the
  delete decision above seen from the other side: whatever retracts a record is also what makes editing one
  possible.

## Two things that are not port gaps but will bite

**A local-development switch is committed in the on state.** `src/data/index.js:4` ships
`const IS_LOCAL = true`, which drops the `/vm` prefix from the resolved API base — the same class of hazard as
the PWA's `js/config.js`, which is sitting on `http://127.0.0.1:54321` with the production Supabase
credentials commented out above it. Both need a deliberate flip before a deploy, and neither has anything
that checks.

**Picklist slug drift — the same list exists under three slugs.** In `core.pkl_values_b` on the local stack,
work type appears as `jfb_work_type`, `pkl-jfb-work-type` **and** `pkl-pkl-jfb-work-type`, all with identical
values; primary measure has the same three-way split (`jfb_primary_measure`, `pkl-jfb-primary-measure`,
`pkl-pkl-jfb-primary-measure`). The doubled `pkl-pkl-` prefix looks like a slug being generated from a value
that already carried one. Harmless while nothing reads them — this app uses only `pkl-jfb-pass-type` and
`pkl-jfb-lift`, and resolves work type from domain columns, not a picklist — but anyone editing a list by
name can easily update a copy nothing reads and conclude the change did not take. Worth pruning to one slug
each before something starts depending on them. Relevant to #30: check which slug the reader actually uses
before adding a value.
